# 一緒に使うと効く部品

[← Family OS の玄関へ戻る](../README.ja.md)

---

Family OS の各モジュールは、単独で動くように作られています。ここに挙げるのは**私たちが作ったものではない部品**で、どれも必須ではありません。ただ、縦軸（1体のAIを育てる）と横軸（家族をつなぐ）の効きは、周りに何を置くかでかなり変わります。

このページは、その「周りに置くもの」の一覧です。製品を推すためではなく、**どういう役割の部品があると効くのか**を先に示すために書いています。役割さえ分かれば、同じ役割の別の道具に置き換えても構いません。

記憶まわりは、**貯める → 引く → 届ける → 守る** の4つに分けて考えると迷いません。その手前に、端末をまたぐなら必ず要る前提がひとつあります。

---

## 端末をまたぐなら、まずここ

AIエージェントを1台のパソコンだけで動かすなら、この節は飛ばして構いません。

ただし、手元のパソコン・サーバー・別の端末にエージェントを分けて置くなら、**まず端末同士が安全に届く状態**を作るのが先です。ここが無いと、このあとの同期もバックアップも横断検索も、そもそも成立しません。

そのための道具が [Tailscale](https://tailscale.com/) のような、端末同士を直接つなぐネットワークです。ポートを外に開けずに済むので、公開サーバーを立てるより安全に始められます。

> **メモ:** ここを飛ばして各端末を個別に設定すると、あとから必ず「どの端末のどのデータが正なのか」で詰まります。順番として最初に置いてください。

| --- | --- | --- |

| 貯める | 生ログの保管 | 「あのとき何と言ったか」を後から正確にたどれる |
| 貯める | ノート基盤 | 人とAIが同じ場所を読み書きし、決定と経緯が1か所に残る |
| 貯める | 長期記憶サービス | セッションをまたいで文脈が残り、説明のやり直しが減る |
| 引く | 全文検索 | 語で引ける。量が増えても効き続ける |
| 引く | ベクトル検索 | 語が違っても意味で引ける |
| 引く | セッション検索 | 自分の過去の会話だけを速く引ける |
| 引く | ナレッジグラフ | 人・案件・決定の**関係**をたどれる |
| 引く | 検索の統一窓口 | 「どこに聞けば見つかるか」を覚えなくてよくなる |
| 引く | コードシンボル検索 | 「どこから呼ばれている？」に、ファイル丸読みなしで今のコードから答えが返る |
| 届ける | ホットキャッシュ | 毎回いちばん大事な要約が自動で目に入る |
| 届ける | ファイル同期 | どの端末からでも同じものを見て書ける |
| 守る | ファイル群のバックアップ | 設定や人格ファイルを壊しても、履歴から戻せる |
| 守る | データベースの複製 | 生ログやナレッジグラフが飛んでも戻せる |
| 守る | 鮮度の監視 | バックアップが止まったことに、必要になる前に気づける |

## 貯める

**生ログの保管。** エージェントとのやり取りを、要約せずそのまま残しておく層です。要約は情報を落とすので、後から「本当は何と言ったか」を確かめる手段が別に要ります。エージェントの実行環境ごとに形式は違い、会話ログのファイル群をそのまま持つもの、データベースに入れるもの、専用のプラグインで丸ごと保つもの（OpenClaw の LCM / Lossless Claw など）があります。**自分の環境の生ログがどこに、どの形式であるかを最初に把握してください。**

**ノート基盤。** 人とAIが同じファイル群を読み書きする場所です。決定・経緯・人物・案件を1か所に集めておくと、横軸でつないだときにエージェント同士が同じものを見て話せます。プレーンな Markdown のディレクトリで十分に成立し、リンクとグラフ表示が要るなら [Obsidian](https://obsidian.md/) のようなツールが向いています。

コツは、**「人が書く場所」と「機械が書く場所」を最初に分ける**ことです。混ざると、どちらかが必ず上書き事故を起こします。

**長期記憶サービス。** 会話や作業の記録をセッションの外に置くための部品です。エージェントの文脈ウィンドウは必ず一杯になるので、外に置き場所があると「毎回はじめから説明する」がなくなります。[Supermemory](https://supermemory.ai/) のようなサービスがこの役割です。

> **メモ:** 何を外に置くかは、そのまま「何が外部サービスに渡るか」です。人格・関係・未公開の判断が含まれる場合は、置く前に線を引いてください。Family OS はこの判断を代行しません。

## 引く

貯めただけでは効きません。**引ける状態になって初めて記憶になります。** 引き方は1種類では足りず、性質の違う検索を併存させるのが実際的です。

- **全文検索** — 語でそのまま引く。記録が増えても速度が落ちにくい。[Meilisearch](https://www.meilisearch.com/) のような軽量なものが扱いやすい
- **ベクトル検索** — 語が違っても意味で引く。埋め込み（embedding）モデルを通して数値にし、近いものを探す
- **セッション検索** — 自分の過去の会話だけを対象に引く。実行環境が持つ全文検索機能で足りることが多い
- **ナレッジグラフ** — 人・案件・決定を点、関わりを線として持ち、関係をたどる。扱う対象が少ないうちは要らない
- **検索の統一窓口** — 上のいくつかを並列に叩いて結果をまとめる薄い層。**あると体感が変わる**

最後の統一窓口は、道具ではなく**自分で書く数十行のスクリプト**で構いません。これが無いと、使う側が「これは全文検索、これはベクトル検索」と毎回選ぶことになり、結局いちばん手近な1つしか使われなくなります。

引く層にはもうひとつ、記憶ではなくコードを対象にした役割があります。ここに置いているのは、失敗の形がまったく同じだからです。

**コードシンボル検索。** 既存のコードベースで作業するエージェントは、「この関数はどこで定義されている？」「どこから呼ばれている？」を絶えず必要とします。素朴な解であるファイル丸読みは、答え**以外**のすべてで文脈ウィンドウを溢れさせます。これを直す役割が、エディタと同じ言語サーバー（LSP）を土台に、シンボル単位の質問に**その場で**答えるサーバーです。[Serena](https://github.com/oraios/serena) が MCP サーバーとしてこの役割を担い、シンボルの定義・参照・ファイルのシンボル一覧だけを返します。

私たちは別解で失敗してから、この役割にたどり着きました。コードベースの静的な地図を先に作る2つのツールを比較したところ、どちらも同じ2つの欠陥 — **コードに存在しない辺**と、**コードが動いた瞬間に古くなる地図** — を抱えていました。クエリ時の解決は、その2つが両方間違えた実際の「どこから呼ばれている？」に正答しました。索引した時点ではなく、**いまのコード**に対して問いを解決するからです。

日常使用から、正直な注意点を2つ:

- **品質は言語サーバー次第。** Python はほぼ設定なしで動きます。Swift はビルドサーバーを配線するまで参照検索が**沈黙して空を返し**ます（エラーは出ません）。シェルスクリプトは関数単位の粗さまでです
- **索引の鮮度は、最後のビルド／インデックス実行まで。** 書いたばかりのコードへの参照は、再ビルドまで出ないことがあります

このページの他の部品と同じく、道具は入れ替え可能です。役割 — **作り置きの地図でもファイル丸読みでもなく、クエリ時に解決するシンボル単位の回答** — が本体です。

## 届ける

**ホットキャッシュ。** いま何が起きているかの要約を1ファイルにまとめ、**セッションの開始時に自動で読ませる**仕組みです。検索は「探しにいく」もので、探しにいかなければ届きません。毎回必ず知っておいてほしいことは、検索ではなく注入で届けます。

小さく保つのがコツです。上限を決めて、溢れたら古いものから落とす。大きくすると読まれなくなり、結局注入する意味がなくなります。

**ファイル同期。** ノート基盤や作業用のファイル群を、端末をまたいで同じ状態に保つ層です。[Syncthing](https://syncthing.net/) のような端末間同期ツールで、共有ディレクトリを1つ決めて揃えます。前提の端末間ネットワークが効いてくるのはここです。

**どちらが正なのかを先に決めてください。** どの端末の内容を正とするのか、双方向にするのか片方向にするのか。決めずに全端末から書ける状態にすると、いつか必ず食い違います。

---

## 守る

貯めたものは、いつか壊れます。**守る層は、ほかの3層すべてにかかります。**

> **メモ:** 同期はバックアップではありません。同期は「いまの状態」を揃える仕組みなので、1台で消したファイルは全端末から消えます。守る層を別に持っていないと、事故が全端末へ同期されて終わりです。

**ファイル群のバックアップ。** 設定・人格ファイル・作業物のように、**履歴で戻したいもの**を守ります。Git ホスティング（GitHub など）へ定期的に push する形が扱いやすく、いつ何が変わったかを後から追えます。エージェントごとに置き場を分けておくと、1体だけ巻き戻すこともできます。

**データベースの複製。** 生ログやナレッジグラフのように、**履歴ではなく中身を丸ごと戻したいもの**を守ります。データベースをクラウドへ複製する仕組み（[Turso](https://turso.tech/) のようなもの）が使えます。

この2つは守る対象が違うので、**どちらか一方では足りません。**ファイル群の履歴があってもデータベースは戻せず、データベースの複製があっても設定は戻せません。

**鮮度の監視。** バックアップが**いつ最後に成功したか**を、どこか1か所で見られるようにします。これが無いと、止まったことに必要になるまで気づけません。

## 自分の環境ではどこにあるか

ここまでの役割は、実行環境によって「すでに持っているもの」と「足す必要があるもの」が違います。まず自分の環境で埋まっている枠を確かめてから、空いている枠だけ足してください。

> **メモ:** 下の表は、私たちが実運用している3つの環境で確認した範囲です（2026-07-06 時点）。バージョンと設定で変わるので、最終的には自分の環境で確かめてください。

| 役割 | Claude Code | Hermes Agent | OpenClaw |
| --- | --- | --- | --- |
| 生ログの保管 | 会話ログの JSONL ファイル群 | SQLite 1つ（全文検索を同梱） | SQLite のセッション保管 ＋ LCM プラグイン |
| セッション検索 | ログを直接引く、または外部インデックスへ載せる | 内蔵の全文検索 | 内蔵の memorySearch |
| ベクトル検索 | 標準では持たない | 標準では持たない | memorySearch が埋め込みモデル経由で担当 |
| 全文検索（横断） | 外部を足す | 外部を足す | 外部を足す |
| 長期記憶サービス | プラグインで接続する | 明示的な保存で接続する | 接続は自前で用意する |

「標準では持たない」は、その環境が劣っているという意味ではありません。**足せば埋まる枠**という意味です。逆に、すでに埋まっている枠に同じ役割を重ねると、どちらが正なのか分からなくなります。

横断検索だけは、どの環境も外部を足す前提になります。ここが**複数の環境を1つの家族として運用するときの、最初の共通作業**です。

## よくある失敗

どちらも私たち自身が踏んだものです。

**1. 配ったのに、誰の検索面にも載っていない。**

ナレッジグラフを作り、各端末へ配布まで自動化したのに、そのデータを**どの検索窓口も見ていなかった**ことがあります。仕組みとしては完成していて、実際には一度も引かれない。置くことと引けることは別で、置いた側は完成した気になりやすい、という典型でした。

新しい層を足すときは、**同時に「これはどこから引かれるのか」を決めてください。**引き手が決まっていない層は、動いていても使われていません。

**2. バックアップが、静かに止まっている。**

十数個のバックアップ先を動かしていて、そのうち数個が**数ヶ月止まったまま**だったことに、後から気づきました。鍵の期限切れ、パスの変更、容量超過 — 止まる理由はいくらでもありますが、共通しているのは**止まっても何も起きない**ことです。エラーは誰も見ていない場所に出て、必要になるまで発覚しません。

だから鮮度の監視を、守る層の役割として独立させています。**バックアップは「設定した」で終わりません。動いていることを別の仕組みが見張って、初めて守れています。**

## 選ぶ順番

全部を最初から揃える必要はありません。順番はだいたいこうなります。

1. **端末間ネットワーク** — 複数端末を使うなら最初。1台だけなら不要
2. **ノート基盤とファイル同期** — 人とAIの共有地。これが無いと他の部品の置き場所も決まらない
3. **ファイル群のバックアップ** — 共有地ができた直後に。**育てはじめてからでは、失うものが増えています**
4. **生ログの把握** — 新しく入れるというより、いまどこにあるかを確認する
5. **長期記憶サービスと全文検索** — 「毎回説明し直す」「目で探せない」が実際に苦になってから

そのあとは、必要になった順で構いません。検索が2系統を超えたら**統一窓口**、毎回必ず届けたいものが固まったら**ホットキャッシュ**、関係を引きたくなったら**ナレッジグラフ**、データベースが育ってきたら**複製と鮮度の監視**。

守る層だけは、後回しにすると取り返しがつきません。**3番目に置いているのはそのためです。**
